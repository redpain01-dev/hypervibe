# HyperVibe 기획서

> `coding.hyperdoctor.app` — 의사를 위한 바이브 코딩 입문 가이드

최종 수정: 2026-07-28 · 상태: 초안(v0.1)

---

## 1. 프로젝트 정의

**한 줄 정의**
코딩을 배운 적 없는 의사가, AI 도구를 이용해 "우리 의원에 필요한 작은 웹 도구"를 직접 만들어 **배포까지 완주**하게 만드는 학습 사이트.

**핵심 성공 기준**
"바이브 코딩을 이해했다"가 아니라 **"내 이름으로 된 URL 하나를 갖게 됐다"**.
의사 대상 교육에서 가장 강력한 동기는 개념 이해가 아니라 완성된 결과물이다. 그리고 HyperDoctor 본체(개원 일정 계산기, 손익분기점 계산기 등)가 이미 그 결과물의 살아있는 예시라는 점을 설득 재료로 사용한다.

**하지 않을 것**
- 개발자 양성 과정이 아니다. 자료구조, 알고리즘, 언어 문법을 가르치지 않는다.
- 특정 툴의 유료 플랜을 파는 곳이 아니다. 무료로 어디까지 되는지를 먼저 말한다.
- 법률·규제 자문을 제공하지 않는다. 경계선을 알려주고 확인처를 연결한다.

## 2. 타깃 페르소나

| | P1 탐색형 | P2 결과물형 | P3 구축형 |
|---|---|---|---|
| 상황 | 40~50대 개원의. ChatGPT는 써봤지만 코딩은 0 | 30~40대 봉직의. 만들고 싶은 게 이미 있음 | Cursor를 설치했다가 막혀서 포기함 |
| 질문 | "내가 진짜 할 수 있나?" | "제일 빠른 길이 뭐야?" | "왜 안 되지?" |
| 필요한 것 | 5분 안의 확신, 성공 사례 | 최단 완주 경로 | 툴 심화, 에러 대처, 배포 |
| 진입 지점 | `/` → `/concept` | `/start` → `/build` | `/tools` → `/help` |

세 페르소나 모두 **시간이 없고, 실패에 대한 인내심이 낮으며, 전문 영역에서는 최고 수준의 학습 능력을 가진 사람**이다. 그래서 설명을 유치하게 낮추면 안 되고, 대신 **낯선 용어를 아는 언어로 번역**해줘야 한다. 이것이 이 사이트의 설계 원칙 전체를 관통한다.

## 3. 차별점

다른 코딩 입문 콘텐츠와 이 사이트를 가르는 세 가지.

**1) 의학 비유 기반 용어 번역**
`repository`를 "저장소"라고 번역하면 아무것도 전달되지 않는다. "환자 차트철"이라고 하면 즉시 이해된다. `debugging`은 "감별진단"이고, `error log`는 "무섭게 생겼지만 그대로 읽으면 되는 검사 결과지"다. 용어 사전을 부록이 아니라 **1급 기능**으로 배치한다.

**2) 의료인 특화 리스크 섹션**
환자정보를 AI에 입력하면 안 되는 이유, 만든 도구가 의료기기 소프트웨어(SaMD)로 분류될 수 있는 경계선, 의원 홍보 페이지의 의료광고 심의 문제. 어떤 일반 코딩 강의에도 없고, 의사에게는 반드시 필요하다.

**3) 같은 과제 · 다른 툴 비교 실습**
동일한 결과물(우리 의원 안내 페이지)을 대화형·웹빌더형·에디터형 세 가지로 만들어보게 한다. 툴 소개를 나열하는 대신 **차이를 체감**시킨다.

## 5. 페이지별 설계

### `/` 랜딩
- **히어로**: "진료실에서 필요한 도구, 직접 만들 수 있습니다." + 부제로 기대치 조정("개발자가 되라는 뜻이 아닙니다")
- **증거 섹션**: HyperDoctor의 기존 무료 도구들을 "이런 것들이 바이브 코딩으로 만들어졌습니다"로 제시. 추상적 약속보다 강력하다.
- **경로 선택**: 3개 페르소나에 대응하는 진입 카드 (처음이에요 / 만들고 싶은 게 있어요 / 하다가 막혔어요)
- **진단 CTA**: `/diagnosis` 유도
- **안전 고지 배너**: "환자 정보는 절대 입력하지 마세요" → `/safety` 링크

### `/concept` 바이브 코딩이란
개념 정의보다 **경계 설정**이 목적. 다룰 내용:
- 바이브 코딩 = 자연어로 요구사항을 말하면 AI가 코드를 쓰고, 사람은 결과를 보고 고쳐달라고 말하는 방식
- 의사가 이걸 잘할 수 있는 이유: 문제 정의 능력, 프로토콜 사고, 검증 습관
- **만들 수 있는 것**: 계산기, 체크리스트, 안내 페이지, 문진표, 자료 정리 도구, 원내 대시보드
- **만들기 어려운 것**: EMR 연동, 결제, 환자 데이터 저장, 다중 사용자 인증 → 왜 어려운지와 언제 전문가가 필요한지
- 기대치 조정: 한 번에 완성되지 않고, 3~5회 왕복이 정상이다

### `/diagnosis` 툴 진단 [인터랙티브]
4~5개 질문으로 3개 트랙 중 하나를 추천.
- 무엇을 만들고 싶은가 (한 페이지 / 여러 화면 앱 / 데이터 처리)
- 프로그램 설치가 가능한 환경인가 (병원 PC 설치 제한 여부는 실제로 큰 변수)
- 월 유료 결제 의향
- 결과물을 남에게 공개할 것인가
- 이전 시도 경험

결과: 추천 트랙 + 이유 + 예상 소요시간 + 대안 1개. 결과는 URL 쿼리로 공유 가능하게.

### `/tools/*` 툴 트랙 (3종)
각 트랙 공통 템플릿:
1. 한 줄 요약과 적합한 사람
2. 비용 (무료 한도 명시)
3. **첫 30분** — 계정 생성부터 첫 결과물까지 단계별
4. 이 툴에서만 통하는 프롬프트 요령
5. 자주 막히는 지점 3가지와 해결
6. 다음 단계 (배포로 연결)

### `/build` 실습
과제: **우리 의원 안내 페이지** (진료시간, 오시는 길, 진료과목, 연락처)
- 왜 이 과제인가: 결과물이 즉시 쓸모 있고, 환자정보가 개입하지 않으며, 배포까지 자연스럽게 이어진다
- 3개 툴 각각으로 만드는 과정을 병렬 제시 → 탭 전환으로 비교
- 완성 예시 데모 제공

### `/deploy` 배포
- "배포 = 개원" 비유로 개념 설명
- 무료 배포 경로: Vercel / Cloudflare Pages / GitHub Pages 비교
- 도메인 구입과 연결
- **HyperDoctor처럼 서브도메인으로 운영하는 법** — 이 사이트 자체가 실제 사례

### `/safety` 의료인을 위한 주의사항
1. **AI에 환자 식별정보 입력 금지** — 개인정보보호법, 의료법상 비밀누설 금지. 프롬프트에 넣은 순간 외부 전송이다
2. **만든 도구에 환자정보 저장 금지** — HyperDoctor의 "브라우저 안에서만 계산" 원칙을 그대로 승계
3. **의료기기 소프트웨어(SaMD) 경계선** — 진단·치료 판단에 관여하면 규제 대상이 될 수 있음
4. **의료광고 심의** — 의원 홍보 페이지는 의료광고에 해당할 수 있음
5. **AI 생성물의 검증 책임** — 계산 로직은 반드시 손으로 검산
6. **라이선스·저작권** — 이미지, 폰트, 오픈소스

각 항목에 "이건 괜찮다 / 이건 위험하다" 대조표. 하단에 "법률 자문이 아니며 관계기관 공식 자료 확인 필요" 고지.

### `/prompts` 프롬프트 라이브러리 [인터랙티브]
카테고리: 시작 / 수정 요청 / 에러 해결 / 디자인 다듬기 / 배포 / 안전하게 요청하기
각 항목: 상황 설명 + 복사 가능한 프롬프트 + 채워 넣을 자리 표시 + 사용 팁

### `/glossary` 용어 사전 [인터랙티브]
검색 + 카테고리 필터. 각 항목은 **영문 용어 / 의학 비유 / 실제 의미 / 언제 마주치나** 4단 구성.

초기 수록 예시:
| 용어 | 의학 비유 |
|---|---|
| repository | 환자 차트철 — 한 프로젝트의 모든 기록이 모인 곳 |
| commit | 경과 기록(progress note) — 그 시점의 상태를 남김 |
| branch | 시험적 치료 arm — 본 흐름을 건드리지 않고 다른 방법 시도 |
| merge | 협진 결과 통합 |
| deploy | 개원 — 원내에서만 되던 걸 외부에 공개 |
| localhost | 원내 전용 |
| bug / debugging | 증상 / 감별진단 |
| error log | 검사 결과지 — 무섭게 생겼지만 그대로 AI에 붙여넣으면 됨 |
| dependency | 병용 약제 — 하나 바꾸면 다른 게 영향받음 |
| framework | 진료 프로토콜 — 매번 처음부터 정하지 않게 해주는 틀 |
| API | 타과 의뢰(consult) — 정해진 형식으로 요청하면 정해진 형식으로 회신 |
| frontend / backend | 진료실 / 검사실 |
| refactoring | 차트 정리 — 내용은 그대로, 읽기 쉽게 |
| version | 가이드라인 개정판 |

## 6. 디자인 방향

HyperDoctor 본체 톤을 상속한다.
- 화이트 기반의 절제된 레이아웃, 카드형 구성
- 섹션 라벨은 대문자 영문 + 한글 헤드라인 조합 (`CORE SIGNAL 01` 패턴)
- 넘버링을 통한 순서 감각

학습 사이트로서 추가할 요소
- **진행감**: 스텝 번호, 현재 위치 표시
- **코드블록 가독성**: 복사 버튼, 줄바꿈 처리, "이 부분만 바꾸세요" 하이라이트
- **스크린샷 중심**: 초보자에게는 글보다 화면 캡처가 압도적으로 효과적
- **불안 완화 장치**: "여기서 막히는 게 정상입니다" 류의 안심 박스를 고정 컴포넌트로

## 7. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js (App Router) | 기존 서브도메인 앱들과 통일 |
| 언어 | TypeScript | |
| 스타일 | Tailwind CSS | |
| 빌드 | `output: 'export'` 정적 생성 | 서버 불필요, 비용 0 |
| 호스팅 | Cloudflare Pages | 본체·`fm` 서브도메인과 동일 |
| 데이터 | 없음. 콘텐츠는 TS 상수로 관리 | 브랜드 원칙(수집 없음) 준수 |
| 상태 저장 | localStorage만 | 회원가입 없음 |
| 분석 | 미정 — 개인정보 최소 수집 도구 한정 | |

**아키텍처 원칙**: 서버가 없다. 모든 페이지는 빌드 시점에 HTML로 생성되고, 인터랙티브 기능 3종만 클라이언트 컴포넌트로 동작한다. 사용자 입력은 어떤 경우에도 외부로 전송되지 않는다.

## 8. 배포

1. GitHub 저장소 생성 후 푸시
2. Cloudflare Pages 프로젝트 연결, 빌드 명령 `npm run build`, 출력 디렉터리 `out`
3. Custom domain에 `coding.hyperdoctor.app` 추가
4. `hyperdoctor.app` DNS에 CNAME 레코드 추가
5. 본체 사이트의 도구 목록에 카드 추가

## 10. 열린 질문

- 브랜드 캐릭터 "하코"를 이 사이트에서도 등장시킬 것인가
- 툴별 스크린샷을 실제 촬영할 것인가, 일러스트로 대체할 것인가 (툴 UI는 자주 바뀌므로 유지보수 비용 고려)
- 무료/유료 정보는 변동이 잦으므로 "최종 확인일" 표기 체계 필요 (본체 저널의 검토일 표기 방식 승계)
